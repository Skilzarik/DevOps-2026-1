# Правила внесения изменений

Этот документ описывает процесс разработки, стандарты кодирования и требования к приёмке изменений в проекте «Музыкальный магазин».

---

## 1. Обязательные команды проверки

Единый интерфейс - `make` (список команд: `make help`). Подробное назначение каждой проверки: [docs/VERIFY.md](docs/VERIFY.md).

| Команда | Назначение |
|---|---|
| `make setup` | первоначальная настройка: окружение, зависимости, базы данных, миграции |
| `make run` | локальный запуск приложения |
| `make test` | unit- и интеграционные тесты, покрытие, отчёты в `backend/reports/` |
| `make quality` | линтер и проверка форматирования (ruff) |
| `make sast` | статический анализ безопасности (bandit) |
| `make migrate` | применить миграции к рабочей БД |
| `make backup` / `make restore FILE=...` | резервная копия и восстановление БД |
| `make mutate` | мутационная проверка: тесты должны замечать изменение условий |
| **`make verify`** | **полный набор обязательных проверок: `policy`, `quality`, `sast`, `test`** |

Pull Request можно создавать только при зелёном `make verify`. Результат прогона вставляется в описание PR.

---

## 2. Запрещённые действия

**Запрещено:**

- Пушить напрямую в ветку `main` в обход Pull Request
- Коммитить файлы `.env` и `.env.test` с реальными секретами (только `*.example`)
- Коммитить папки `__pycache__/`, `venv/`, `backend/reports/`, `backups/`, `.vscode/`
- Использовать `git push --force` в общие ветки
- Добавлять в код захардкоженные пароли, токены или строки подключения к БД
- Менять схему БД напрямую через SQL-скрипты - только через Alembic-миграции
- Править уже применённую миграцию: изменения схемы вносятся только новой ревизией
- Удалять тесты, помечать их `skip`/`xfail` или ослаблять проверки, чтобы пройти `make verify`
- Снижать порог покрытия (`fail_under`) и значения в `quality-baseline.txt` (их можно только повышать)
- Добавлять исключения анализаторов (`# noqa`, `# nosec`, `ignore`, `skips`) без письменного обоснования
- Сливать изменения при красном `make verify`

**Если исключение действительно необходимо**, оно оформляется явно и объясняется:

- `# noqa: E501 -- длинная строка в SQL, разбить нельзя` (после `--` обязательна причина);
- `# justified: <причина не короче 10 символов>` на строке с `skip`/`xfail`;
- в описании Pull Request отдельным пунктом: что отключено и почему.

**Критические файлы приёмки** - любое их изменение выделяется в описании PR и проверяется отдельно:
`Makefile`, `backend/pyproject.toml`, `quality-baseline.txt`, `scripts/check_policy.py`,
`backend/tests/conftest.py`, `docs/TRACEABILITY.md`, `backend/ale/versions/*`.

Эти правила проверяет `make policy` (входит в `make verify`), но он не заменяет код-ревью.

## 2а. Контейнерное окружение (Лаб. 4)

Команды: `make up`, `make down`, `make container-check`, `make container-backup`,
`make container-restore FILE=...`. Описание: [docs/CONTAINERS.md](docs/CONTAINERS.md).

Изменения `Dockerfile`, `compose.yaml`, `docker/` разрешено вносить в Pull Request только после
успешного `make container-check` (его результат прикладывается к PR).

**Запрещено:**

- тег `latest` и образы без явного тега;
- запуск процессов от root (в Dockerfile обязателен `USER` с непривилегированным пользователем);
- секреты в образе, в `Dockerfile` и в `compose.yaml` (только переменные окружения из `.env.docker`,
  которого нет в git);
- отключение healthcheck (`disable: true`, `HEALTHCHECK NONE`);
- публикация портов, кроме порта nginx: порты БД и приложения наружу не открываются;
- контейнеры без лимитов памяти и процессора; `privileged`, `network_mode: host`, монтирование `docker.sock`.

Эти правила проверяет `scripts/check_container_policy.py` (входит в `make container-check`).

**Критические файлы приёмки:** `Dockerfile`, `.dockerignore`, `compose.yaml`, `docker/**`,
`scripts/container_check.sh`, `scripts/check_container_policy.py`. Любое их изменение выделяется в описании PR.

## 3. Стиль коммитов

Используется стандарт **Conventional Commits**:

```
<тип>(<область>): <краткое описание>

[опциональное тело коммита]

[опциональные ссылки на задачи]
```

### Допустимые типы

- `feat` — новая функциональность
- `fix` — исправление ошибки
- `docs` — изменения в документации
- `style` — форматирование, без изменения логики
- `refactor` — рефакторинг кода
- `test` — добавление тестов
- `chore` — рутинные задачи (обновление зависимостей, CI)

### Примеры

```
feat(auth): add JWT token refresh endpoint
fix(sales): prevent negative stock on sale
docs(readme): update deployment instructions
chore(deps): upgrade fastapi to 0.115.0
```

## 4. Порядок работы с ветками

1. Создайте новую ветку от актуальной `main`:
   ```bash
   git checkout main
   git pull origin main
   git checkout -b feature/название-фичи
   ```

2. Делайте осмысленные коммиты по мере выполнения задач

3. Перед созданием PR синхронизируйтесь с `main`:
   ```bash
   git fetch origin
   git rebase origin/main
   ```

4. Запушьте ветку и создайте Pull Request:
   ```bash
   git push origin feature/название-фичи
   ```

---

## 5. Требования к Pull Request

Pull Request считается готовым к ревью, если:

- У него есть понятное название и описание изменений
- Размер PR не превышает **400 строк кода** (крупные фичи разбиваются на несколько PR)
- Все автоматические проверки (линтеры, тесты) проходят успешно
- Код соответствует стилю проекта (PEP 8 для Python)
- Нет конфликтов с веткой `main`
- Добавлена/обновлена документация (при необходимости)

---

## 6. Порядок приёмки (Code Review)

1. Минимум **1 одобрение (approve)** от ментора
2. Все комментарии в Code Review должны быть разрешены до мержа
3. После мержа ветка-источник удаляется

---

## 7. Разрешение конфликтов

Если при rebase/merge возникли конфликты:

1. Разрешите конфликты вручную в затронутых файлах
2. Добавьте изменённые файлы:
   ```bash
   git add <файлы>
   ```
3. Завершите операцию:
   - Для merge:
     ```bash
     git commit
     ```
   - Для rebase:
     ```bash
     git rebase --continue
     ```
4. Сделайте push в свою ветку:
   ```bash
   git push origin feature/название-фичи
   ```

---

## 8. Релизы и теги

- Первая стабильная версия отмечается тегом `v0.1.0`
- Теги создаются только от ветки `main`:
  ```bash
  git tag -a v0.1.0 -m "First stable release"
  git push origin v0.1.0
  ```
