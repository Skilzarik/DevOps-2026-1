# Правила внесения изменений

Этот документ описывает процесс разработки, стандарты кодирования и требования к приёмке изменений в проекте «Музыкальный магазин».

---

## 1. Обязательные команды проверки

Перед созданием Pull Request необходимо убедиться, что код проходит следующие проверки:

### Линтинг и форматирование

```bash
# Проверка стиля кода (Python)
ruff check .

# Автоматическое форматирование
black .

# Сортировка импортов
isort .
```

### Тестирование

```bash
# Запуск тестов (если реализованы)
pytest

# Проверка работоспособности API
curl http://localhost:8000/health
```

### Проверка миграций

```bash
# Убедитесь, что миграции применяются без ошибок
alembic upgrade head
```

## 2. Запрещённые действия

**Запрещено:**

- Пушить напрямую в ветку `main` в обход Pull Request
- Коммитить файлы `.env` с реальными секретами (только `.env.example`)
- Коммитить папки `__pycache__/`, `venv/`, `node_modules/`, `.vscode/`
- Использовать `git push --force` в общие ветки
- Добавлять в код захардкоженные пароли, токены или строки подключения к БД
- Менять схему БД напрямую через SQL-скрипты — только через Alembic-миграции

## 3. Стиль коммитов

Используется стандарт **Conventional Commits**:

```
<тип>(<область>): <краткое описание>

[опциональное тело коммита]

[опциональные ссылки на задачи]
```

### Допустимые типы

- `feat` — новая функциональность
- `fix` — исправление ошибки
- `docs` — изменения в документации
- `style` — форматирование, без изменения логики
- `refactor` — рефакторинг кода
- `test` — добавление тестов
- `chore` — рутинные задачи (обновление зависимостей, CI)

### Примеры

```
feat(auth): add JWT token refresh endpoint
fix(sales): prevent negative stock on sale
docs(readme): update deployment instructions
chore(deps): upgrade fastapi to 0.115.0
```

## 4. Порядок работы с ветками

1. Создайте новую ветку от актуальной `main`:
   ```bash
   git checkout main
   git pull origin main
   git checkout -b feature/название-фичи
   ```

2. Делайте осмысленные коммиты по мере выполнения задач

3. Перед созданием PR синхронизируйтесь с `main`:
   ```bash
   git fetch origin
   git rebase origin/main
   ```

4. Запушьте ветку и создайте Pull Request:
   ```bash
   git push origin feature/название-фичи
   ```

---

## 5. Требования к Pull Request

Pull Request считается готовым к ревью, если:

- У него есть понятное название и описание изменений
- Размер PR не превышает **400 строк кода** (крупные фичи разбиваются на несколько PR)
- Все автоматические проверки (линтеры, тесты) проходят успешно
- Код соответствует стилю проекта (PEP 8 для Python)
- Нет конфликтов с веткой `main`
- Добавлена/обновлена документация (при необходимости)

---

## 6. Порядок приёмки (Code Review)

1. Минимум **1 одобрение (approve)** от ментора
2. Все комментарии в Code Review должны быть разрешены до мержа
3. После мержа ветка-источник удаляется

---

## 7. Разрешение конфликтов

Если при rebase/merge возникли конфликты:

1. Разрешите конфликты вручную в затронутых файлах
2. Добавьте изменённые файлы:
   ```bash
   git add <файлы>
   ```
3. Завершите операцию:
   - Для merge:
     ```bash
     git commit
     ```
   - Для rebase:
     ```bash
     git rebase --continue
     ```
4. Сделайте push в свою ветку:
   ```bash
   git push origin feature/название-фичи
   ```

---

## 8. Релизы и теги

- Первая стабильная версия отмечается тегом `v0.1.0`
- Теги создаются только от ветки `main`:
  ```bash
  git tag -a v0.1.0 -m "First stable release"
  git push origin v0.1.0
  ```
