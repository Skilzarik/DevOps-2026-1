# Контейнерное окружение (Лаб. 4)

Запуск, проверка и обслуживание приложения в Docker. Всё выполняется на Linux-машине (виртуальной машине) с Docker.

## Схема

```
клиент ──► nginx :80 ──► app1 :8000 ─┐
          (edge + backend)  app2 :8000 ─┼──► db :5432 (volume pgdata)
                                   migrate (одноразово)
```

| Сервис | Образ | Назначение | Порты наружу |
|---|---|---|---|
| `nginx` | `nginxinc/nginx-unprivileged:1.28-alpine` | единственная точка входа, балансировка, ограничение частоты | только 80 (в контейнере 8080) |
| `app1`, `app2` | `music-store:<APP_VERSION>` (собирается из `Dockerfile`) | два экземпляра приложения, отличаются `INSTANCE_ID` | нет |
| `db` | `postgres:17-alpine` | PostgreSQL, данные в volume `pgdata` | нет |
| `migrate` | тот же образ приложения | применяет миграции Alembic под ролью `migrator` и завершается | нет |

Сети: `edge` (внешняя, подключён только nginx) и `backend` (`internal: true`, без выхода наружу).
Порядок запуска: `db` healthy, затем `migrate` завершён успешно, затем `app1`/`app2` healthy, затем `nginx`.

## Команды

| Команда | Что делает |
|---|---|
| `make container-env` | создаёт `.env.docker` со случайными паролями (в git не попадает) |
| `make up` | собирает образ, запускает окружение, ждёт готовности всех сервисов |
| `make ps` / `make logs` | состояние и журналы |
| `make down` | останавливает и удаляет контейнеры, **volume с данными сохраняется** |
| `make container-check` | полная автоматическая проверка (см. ниже) |
| `make container-backup` | резервная копия БД в `backups/` |
| `make container-restore FILE=...` | восстановление в текущую БД |
| `make container-restore-new FILE=...` | восстановление в новый volume (отдельный проект `music-restore`) |

## Что проверяет `make container-check`

1. Правила: нет `latest`, `USER` не root, нет секретов в образе и compose, healthcheck не отключён, лишних портов нет, заданы лимиты ресурсов, не менее двух экземпляров.
2. Сборка образа; в образе нет `.env` и секретов; версии зависимостей совпадают с `backend/requirements.txt`.
3. Запуск: все сервисы `healthy`, миграции выполнены (`migrate` завершился с кодом 0).
4. Главные процессы всех контейнеров работают не от root.
5. Порты БД и приложения не опубликованы, наружу открыт только nginx.
6. Через nginx отвечают оба экземпляра (заголовок `X-Instance-ID`).
7. Остановка `app1`: быстро, по SIGTERM (код 0 или 143, не 137), в журнале есть завершение; сервис остаётся доступен.
8. Ограничение частоты: при превышении лимита nginx отвечает 429.
9. Данные сохраняются после `down`/`up` и после обновления образа.
10. Резервная копия и восстановление в новый volume дают те же данные.
11. Лимиты памяти и процессора применены к контейнерам.

## Проверки для защиты (вручную)

```bash
make up
docker compose --env-file .env.docker exec app1 id                      # uid=10001(app): процесс не от root
docker compose --env-file .env.docker exec app1 sh -c 'cat /proc/1/status | grep -i ^uid'
curl -si http://localhost/health | grep -i x-instance-id                # повторить несколько раз: app1, app2

# корректное завершение
time docker compose --env-file .env.docker stop app1                    # секунды, без ожидания таймаута
docker inspect -f '{{.State.ExitCode}}' $(docker compose --env-file .env.docker ps -aq app1)   # 143 (SIGTERM), не 137
docker compose --env-file .env.docker logs app1 | tail -5               # Shutting down ... shutdown complete

# сохранность данных
docker compose --env-file .env.docker down && make up                   # пользователь и данные на месте

# восстановление в новый volume
make container-backup
make container-restore-new FILE=backups/<файл>.dump
```

Код 143 означает, что uvicorn корректно завершился по SIGTERM (128 + 15). Код 137 (128 + 9) означал бы,
что Docker не дождался и убил процесс.

## Ограничения ресурсов и обоснование

| Сервис | Память | CPU | Обоснование |
|---|---|---|---|
| `app1`, `app2` | 256 МБ | 0.5 | один процесс uvicorn с небольшим пулом соединений; запас в несколько раз над типовым потреблением |
| `db` | 512 МБ | 1.0 | `shared_buffers` по умолчанию 128 МБ плюс процессы соединений; данные учебные |
| `nginx` | 64 МБ | 0.25 | прокси без кэширования, потребляет единицы мегабайт |
| `migrate` | 256 МБ | 0.5 | кратковременная задача |

Значения нужно **проверить измерением** и при необходимости скорректировать: запустите окружение, создайте нагрузку
и выполните `docker stats --no-stream`. Лимит должен быть заметно выше пикового потребления (с запасом в 2-3 раза),
но достаточно низким, чтобы один сервис не мог исчерпать память машины. Записанные вами измеренные значения
приложите к отчёту. Дополнительно заданы `pids_limit`, `read_only`, `cap_drop: ALL`, `no-new-privileges`.

## Что мешает горизонтальному масштабированию приложения

1. **Общий секрет.** Токены JWT подписываются `SECRET_KEY`. У всех экземпляров он обязан быть одинаковым, иначе токен, выданный одним экземпляром, отклонит другой. Хорошо, что состояния сессий в памяти нет.
2. **Гонка при продаже.** Проверка остатка и его уменьшение выполняются без блокировки строки. Два экземпляра, обработавшие одновременно продажу последнего диска, могут оба пройти проверку. Страховка: `CHECK (stock >= 0)` в БД (вторая транзакция получит ошибку, но клиент увидит 500). Правильное решение: `SELECT ... FOR UPDATE` или атомарный `UPDATE ... WHERE stock >= :qty`.
3. **Пул соединений на каждый экземпляр.** Каждый экземпляр держит собственный пул (по умолчанию до 15 соединений в SQLAlchemy). Число соединений к PostgreSQL растёт пропорционально числу экземпляров и упрётся в `max_connections`.
4. **Миграции.** Их нельзя выполнять при старте каждого экземпляра, иначе возникает гонка. Поэтому они вынесены в отдельную одноразовую задачу `migrate`.
5. **Один `/health` на всё.** Он отвечает 503 при недоступной БД, поэтому все экземпляры одновременно становятся `unhealthy`. Для оркестратора стоило бы разделить проверку «процесс жив» и «готов принимать трафик».
6. **Единая БД.** Масштабирование приложения не масштабирует PostgreSQL: он остаётся единой точкой отказа (нужна репликация или управляемая БД).
7. **Ограничение частоты на уровне nginx.** Лимит считается в одном nginx. При нескольких балансировщиках потребуется общее хранилище счётчиков.
8. **Раздача статики приложением.** Каждый экземпляр отдаёт интерфейс сам. Это работает, но лучше отдавать статику напрямую из nginx.

## Известные особенности

- **nginx и адреса экземпляров.** Имена `app1`/`app2` разрешаются в IP при запуске nginx. После пересоздания контейнера приложения (новый IP) выполните `docker compose --env-file .env.docker restart nginx`.
- **Docker и ufw.** Опубликованные порты Docker открывает в обход правил ufw. Поэтому единственный публикуемый порт (nginx) нужно контролировать в `compose.yaml`, а не в ufw.
- **POST не повторяется.** `proxy_next_upstream` не повторяет небезопасные методы, поэтому сбой во время оформления продажи не приведёт к дублю.
